# Ferric Oxide: implemented system

Ferric Oxide is a Rust microkernel operating system built on Redox OS. This
section describes the implementation in this repository, including the fork's
build tools and kernel changes. The rest of the book supplies the inherited
Redox background; its historical paths, hardware coverage and implementation
descriptions may differ from this checkout.

## Implementation status

"Implemented" below means that the code and its integration exist. It does not
claim that every machine has been tested, that every configured CI run has
passed, or that a feature is enabled in every image.

| Area | Implemented behavior | Boundary or remaining work |
| --- | --- | --- |
| Monorepo | Local kernel, bootloader, relibc, base services, RedoxFS, installer and Redoxer sources; shared host workspace | Other applications still come from recipes; target builds remain separate |
| Native build | `cargo xtask` setup, image build and QEMU; rustup, host Clang/LLD and rootless image writing; ARM64 UEFI firmware clock handoff ([build guide](ferric-build.md)) | Host architecture by default with explicit x86-64/ARM64 UEFI cross-builds; ARM64 uses a RAM-backed live image/software emulation, with persistent storage, HVF and some applications still incomplete; target GCC ABI runtime data remains; some application recipes need additional tools |
| Feature configuration | TOML catalog, interactive editor, CLI, validation and generation of Make, image and kernel settings; per-architecture minimum CPU baselines and independent variant checkboxes | Target overrides resolve before validation; variant builds produce separate images, with combined-architecture images still future work; no `ferric.toml` preserves the upstream-style build path |
| Device trees | Shared allocation-free adapter around the crates.io `fdt` parser; host-tested console, phandle and MMIO handling ([architecture](ferric-architecture.md)) | ARM64/RISC-V firmware inputs; device bindings and reserved-memory policy remain in the kernel; parser updates need target boot validation |
| CPU state | x86-64-v3 baseline for configured user-space builds; optional v4, AVX and AVX-512 state saving, boot checks; ARM64 signal argument and SIMD/control preservation | Prebuilt packages and toolchain libraries do not acquire local CPU flags |
| Memory protection | Physical-map and kernel-image KASLR, user ASLR, `PROT_NONE` guards, KPTI and PCID support | Address randomization uses RDRAND with a fixed-layout fallback; fixed user mappings are not relocated |
| CET | Optional supervisor IBT and shadow-stack enforcement with private frame pools | Shadow stacks require KPTI off; fresh CET hardware validation is pending (#78); user-mode CET remains off |
| DMA isolation | Intel VT-d and AMD-Vi DMA domains, driver binding, IOVA translation, revocation and an enforce policy | IOMMU defaults to `never`; AMD interrupt remapping is not implemented |
| Registered buffers | Anonymous-memory registration, byte grants, sub-grants, CPU mappings, page-aligned DMA grants with IOVA retirement on revoke, and `nvmed` DMA into an attached grant (`drivers.grant_dma`) | Off by default; partial pages use bounce buffers; disk grants are direct calls on `nvmed` descriptors, with no RedoxFS or ring support; other I/O is not converted |
| Interrupt delivery | Per-(CPU, vector) interrupt counts and events, and a root-only `irq:cpus` map of logical CPU, APIC id and NUMA node (`kernel.irq_percpu`) | Off by default; x86_64 only; `nvmed` can run one I/O queue pair and pinned worker per CPU (`drivers.nvme_percore`, off by default), but the disk scheme spreads requests round-robin, and serves reads and writes concurrently only under the `Workers` queue policy (on QEMU, spilling to per-CPU queues does not beat one queue); root can steer a vector to another CPU (`irq:` `Move` call; VT-d rewrites its remapping entry), but no balancer uses it yet |
| Rings | `kernel.ring` scheme (`kernel.rings`): shared SQ/CQ memory, brokered `Nop`, `Read`, `Write`, `Fsize`, `Fstat` and `Fsync` on any scheme in the caller's context, a fixed-file table, linked chains whose files are held from submission to completion, asynchronous chains on a per-ring kernel worker, `Enter` waiting for `min_complete` completions, CQ back-pressure and `EVENT_READ` notification ([I/O chapter](ferric-io.md)) | Off by default; one worker per ring runs asynchronous chains in order; no grant buffers, `SqPoll` or `Umwait` notification, or rings served natively by user schemes |
| Kernel-bypass networking | `ferric-netq` queue socket ABI, four rings on `ferric-ring`, and copy mode in `driver-network` (`drivers.net_bypass`): software steering filters ahead of netstack, received frames copied into the application's UMEM, TX copied out, port ownership through a netstack socket, TX validation | Off by default; root-only (so any socket may ask for raw TX); no zero-copy mode yet; on-target test `ferric-netq-test` with a TX benchmark against netstack |
| Network drivers | `driver-network` adapters for e1000, ixgbe, RTL8139 and RTL8168, plus `rtl8125d` (`drivers.rtl8125`, default off): MAC and PHY OCP initialisation, RTL8125B MAC/PHY firmware patches, legacy 16-byte descriptors and one RX/TX ring pair, with the register sequence checked against a controller model in host tests | `rtl8125d` claims only the RTL8125B, has compiled but not booted on hardware, and omits jumbo frames, offloads, multiple queues and wake-on-LAN; QEMU does not emulate an RTL8125 |
| Kernel tracing | Typed tracepoints as static keys (`syscall.enter`/`exit`, `sched.switch` and `sched.futex_wait`/`futex_resume`/`futex_wake`, `sched.context_create`/`context_start`/`context_exit`, process lifecycle records `procmgr` writes to `kernel.trace/emit` (`sched.proc_fork`/`proc_exec`/`proc_exit`/`proc_wait`), `scheme.request`/`response`/`cancel` with SQE tags, `mm.page_fault`, `mm.map`/`protect`/`unmap` operation results and a mapping journal (`mm.replace`/`move`/`clone`/`clone_skip`/`destroy`), `irq.deliver`/`ack`, `iommu.fault` and completed `iommu.map`/`protect`/`unmap`), per-CPU rings, boot-time and live enable (also from an initfs `trace.toml` bootstrap applies before init), per-event argument filters (`filter <event> <arg> <op> <value> && ...` on `events`, listed in `filters`), a `kernel.trace` scheme, open by path to root and to others through `cap/read` or `cap/control` capabilities root hands over, with read-only mapping of the rings (`mmap` of `cpu/<n>`, `commit <end>`), a host text view, Perfetto JSON and OpenTelemetry (OTLP/JSON) export (`tools/ferric-trace/`), captures that read the rings through that mapping where the kernel offers it and fall back to reads (`ferric-trace capture --via auto`), an optional crash dump that keeps a panic's message and newest records in reserved RAM across a warm reboot, with flight-recorder rings that overwrite their oldest records when full (`kernel.trace_crash`, read with `ferric-trace crash`), sampling profiles recorded with `ferric-trace profile` and drawn as flamegraphs (`ferric-trace flamegraph`, `kernel.profiling`), and a persistent kernel log whose end the next boot serves as `/scheme/sys/log_previous` (`kernel.log_persist`) | Off by default; x86_64 only; CI holds tracing to a 1% overhead budget compiled in but off (null system calls) and 5% with every event on (RedoxFS requests) |
| `fox` | Local signed archives, installed-file verification, in-place install/remove, CycloneDX SBOMs; replaces `pkg` on the target by default (`packages.manager`), with signed manifests packed by the cookbook; the image build adopts the installed packages with the host `fox`, syncs an optional package set (`packages.set`, `fox.lock`, `packages.locked`) and writes `image.cdx.json`, and a first-boot service adopts any packages still unadopted. `cargo fox` builds a git commit hermetically into a signed archive with a build SBOM and a signed attestation, which `fox verify` checks, and `cargo fox release` makes SSH-signed release tags; `fox install <git-url>` builds a signed release from source, pinning its author key on first use, or installs a prebuilt from an explicitly trusted builder. `fox-registry` creates and signs a git-hosted package registry (`fox-tuf/1`, a TUF subset), checks owners' release tags, builds attested artifacts in registry CI, lets independent rebuilders add matching attestations (`fox-registry rebuild`) and imports cookbook recipes as `recipe` packages; `fox registry`, `fox search`, `fox info` and `fox install <name>` use registries, installing prebuilt artifacts that enough registry builders attest to (the highest x86-64 level the CPU and `max-cpu-level` allow, v3 or v4) and otherwise building the owner-signed tag, under `etc/fox/policy.toml`; `fox audit` matches installed packages and the crates in their build SBOMs against registry and RustSec advisories, setting aside findings a registry's signed CycloneDX VEX statements clear, `fox sbom --system` describes a whole root, and `fox sync` installs a package set and pins it in `fox.lock` | no official registry is published; dependencies are not resolved; dependency solver or generation/rollback store; HTTPS fetching is not built for the target; builds are isolated by environment, not a network sandbox; the installer still places the configuration's packages with `pkg`'s library before `fox` adopts them; the image SBOM is not signed; no wasm variants |
| Page cache (read path) | `kernel.pcache`: file systems keep file contents in kernel objects and the kernel serves `read`/`pread` of attached descriptions from them, filling misses through the file system's queue with readahead; `ferric-pcache` holds the interface and policies, host-tested ([I/O chapter](ferric-io.md#page-cache-read-path)) | `kernel.page_cache`, off by default; RedoxFS serves reads of files opened read-only from it (not while a file has a shared writable mapping); other file systems, mapping files through the cache, writes through it and reclaim come later |
| ext4 (read-only) | `ext4d` (`fs.ext4`): a daemon that serves an ext4 volume read-only as a scheme, from a disk, a byte range of one (`--offset`, `--length`) or an image file. Reading uses the `ext4-view` crate (extents, hashed directories, checksums, journal); caller UID/GID permissions protect reads and directory traversal; writes, creation, removal and renames fail with `EROFS`. With `fs.ext4_journal_replay`, a volume that was not cleanly unmounted has its journal replayed onto the disk first (`ferric-jbd2`); `fs.ext4_write` adds a JBD2 transaction writer, so far used by the scheme's `futimens`, `fchmod` and `fchown` to set a file's times, mode and owner ([I/O chapter](ferric-io.md#ext4-read-only)) | Off by default; started by hand, not by init or the installer; on LUKS or LVM through `ferric-blockd`; inode numbers come from paths (hard links differ), change times from the inode; no `mmap`; the scheme changes only an inode's times, mode and owner (`futimens`, `fchmod`, `fchown`, with `fs.ext4_write`); no external journals or fast commits |
| Block layers (read-only) | `ferric-blockd` (`fs.luks`, `fs.lvm`): a daemon that stacks block layers from its command line and serves the result read-only as a scheme, for a file system daemon such as `ext4d` to mount: LUKS1 and LUKS2 volumes (aes-xts-plain64, 512- to 4096-byte sectors, passphrase from a key file), LVM2 linear and striped logical volumes, and byte windows, in any order (LVM on LUKS, LUKS on LVM). The layers are `ferric-blocklayer`, `no_std`; formats are read by `ferric-luks` (headers, PBKDF2/Argon2 keyslots, data segments) and `ferric-lvm` (labels, metadata, mapping) ([I/O chapter](ferric-io.md#block-layers-luks-and-lvm-read-only)) | Off by default; started by hand, not by init, the installer or the bootloader; only root may open a volume; no writing, keyslot changes, tokens, detached headers or reencryption; mirror, RAID, thin, cache and snapshot LVs are refused |
| FAT (read-only) | `fatd` (`fs.fat`): a daemon that serves a FAT12, FAT16 or FAT32 volume (the EFI system partition, removable media) read-only as a scheme, from a disk, a byte range of one or an image file, through `ferric-blocklayer`. Reading uses the `fatfs` crate; long names are listed, and lookups ignore case and accept 8.3 short names. Files are root's and world-readable, every change fails with `EROFS`, and the device is only opened for reading. With `fs.exfat`, fatd also serves exFAT volumes, read by the optional `ferric-exfat` parser (timestamps and identification are shared in `ferric-fat-types`), a `no_std` reader written from Microsoft's exFAT specification. See [FAT, read-only](./ferric-io.md#fat-read-only) and [exFAT](./ferric-io.md#exfat). | Off by default; no writable FAT or exFAT |
| Disk benchmark | `ferric-iobench`: fio-style read jobs (`--rw`, `--bs`, `--iodepth`, `--numjobs`, `--io_size`, `--randseed`) run on the largest NVMe partition with one positioned read per thread, IOPS, bandwidth and fio-layout latency percentiles, a same-boot A/B of the queue policies, and the matching Linux fio command (`ferric_iobench`, host-tested; [I/O chapter](ferric-io.md#disk-benchmark-ferric-iobench)) | Reads only, `psync` and `--direct=1` only; runs in the smoke image's five CI boots on emulated NVMe, so its numbers are same-boot comparisons; the comparison with fio on Linux on reference hardware has not been run yet |
| Virtualization (prepared) | `ferric-vmx`, `ferric-svm` and `ferric-vm`: VMX and SVM formats (VMCS fields, controls from capability MSRs, EPT entries, entry checks, the VMCB, exit decodings, permission maps) and the planned `kernel.vm` scheme ABI (calls, run page, registers, CPUID table, MSI decoding), as `no_std` crates ([chapter](ferric-virt.md)) | Crates only, host-tested: the kernel has no VMX or SVM backend and no `kernel.vm` scheme, there is no VMM, and no image uses them; no `features.toml` option until the kernel core lands |
| WebAssembly | Host-tested `no_std` crates for the `ferric:sys@1` import ABI and the sealed code-cache entry format (key, MAC, relocations); see [WebAssembly interfaces](./ferric-wasm.md) | Prepared interfaces only: no runtime, compiler service, cache daemon, kernel scheme or recipe uses them yet |
| Validation | Host unit/integration tests, kernel helper and boot-allocator tests, Miri for aligned buffers and queue records, kernel lint ratchet, binary checks, image boot and syscall fuzz workflows | Helper tests do not execute hardware context switches or user-copy faults; configured checks are not evidence of a successful run; hardware coverage depends on reports |

The focus of new Ferric development is modern x86-64 hardware and UEFI. Older
architectures and BIOS code remain in imported sources and recipes for upstream
compatibility; their presence is not a commitment to extend them.
